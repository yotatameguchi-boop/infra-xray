# Infra X-Ray — 要件定義書 v0.1

**ステータス：初期開発仕様案**

## 1. プロダクト概要

### 製品名
Infra X-Ray（仮称）

### キャッチコピー
**See what your infrastructure is becoming.**

### ビジョン
複雑で見えにくいクラウドインフラを、誰もが直感的に理解できるようにする。

### 製品コンセプト
Terraformの変更予定を解析し、インフラ構成・変更箇所・セキュリティ上の確認事項を、インタラクティブなグラフで表示する開発者向けソフトウェア。

### 開発方針
- オープンソース（OSS）として公開する
- ローカル環境で動作する
- 視覚的に優れた操作体験を実現する
- 解析結果の根拠と限界を明示する
- 将来的に商用SaaSへ発展できる構造にする

---

## 2. ターゲットユーザー

### メインターゲット
TerraformでAWSインフラを管理している個人開発者・小規模開発チーム。

### 想定利用者
- インフラエンジニア
- SRE
- DevOpsエンジニア
- バックエンドエンジニア
- セキュリティエンジニア

### 主な課題
1. Terraformの変更内容が直感的に理解しにくい
2. どのリソースが変更されるのか把握しづらい
3. 設定変更によるセキュリティ上の問題を見逃したくない
4. コードレビュー時に構成全体の理解に時間がかかる

## 4. 機能要件

### FR-001：Terraform JSONのインポート

**優先度：必須**

CLIからTerraform plan JSONを指定して読み込める。

想定コマンド：

```bash
infra-xray view plan.json
```

上記CLIは新規に実装する予定のもの。

要件：
- JSONファイルの読み込み
- Terraform JSON形式の検証
- 未対応形式の明確なエラー表示
- 変更情報の抽出
- Terraformが存在する場合、外部コマンドで生成したJSONを利用可能

### FR-002：リソース解析

**優先度：必須**

初期の解析対象：
- aws_instance
- aws_security_group
- aws_vpc_security_group_ingress_rule
- aws_db_instance
- aws_vpc
- aws_subnet
- aws_lb

必要に応じて順次拡張する。

取得する情報：
- リソースのアドレス
- リソース種別
- 変更操作
- 表示可能な依存関係
- 診断に必要な限定的な設定情報

### FR-003：構成グラフの表示

**優先度：必須**

解析結果を2Dのインタラクティブなグラフとして表示する。

要件：
- リソースをノードで表現
- 確認できた関係をエッジで表現
- ズーム・パン
- ノード選択
- 自動レイアウト
- リソースの種類に応じたアイコン
- 関係が確認できない場合は線を作らない

グラフ上の線は、Terraformの依存・参照関係など、意味を明示する。実際のネットワーク通信経路と混同させない。

### FR-004：変更内容の表示

**優先度：必須**

以下の変更種別を識別する。

- Create：新規作成
- Update：更新
- Delete：削除
- Replace：置換
- No Change：変更なし

置換予定のリソースは、単なる更新と区別して表示する。

変更対象の詳細パネルでは、Terraformの変更前後の情報を、公開してよい属性に限定して比較する。

### FR-005：セキュリティ診断

**優先度：必須**

最初のバージョンでは、次の限定的なルールを実装する。

| ID | 診断内容 |
|---|---|
| SG-001 | SSHの許可元が全IPv4アドレスに広がる変更 |
| DB-001 | RDSの `publicly_accessible` が有効になる変更 |
| OPS-001 | RDSの削除・置換予定 |

各ルールは実際のTerraform JSONの形式に基づいて判定する。

診断結果には以下を表示する。
- ルールID
- 対象リソース
- 検出した変更内容
- 確認が必要な理由
- 判定根拠
- 診断できなかった条件

診断結果は安全性を保証するものではなく、確認すべき設定を提示する。

### FR-006：詳細パネル

**優先度：必須**

ノードをクリックすると、右側のパネルで次の内容を確認できる。

- リソース名
- リソース種別
- Terraform上のアドレス
- 変更種別
- 診断結果
- 確認できた依存・参照関係

### FR-007：構成・変更・セキュリティの表示切り替え

**優先度：必須**

画面上部の切り替え操作によって、同じグラフを次の3つの視点で表示する。

**Architecture View**

構成・リソース間の関係を確認する。

**Change View**

変更対象リソースを強調表示する。

**Security View**

セキュリティ上の確認事項を強調表示する。

## 5. UI・UX要件

### デザイン原則

**Visible**
見えないインフラの構造を理解できる。

**Intuitive**
大量の設定情報から重要な部分を直感的に発見できる。

**Trustworthy**
すべての診断に根拠があり、判定できない部分も明確である。

### デザイン仕様
- ダークテーマを基本とする
- 余白を生かしたミニマルなデザイン
- リソースごとに統一したアイコン
- 変更・警告を色と形状の両方で区別
- 滑らかで控えめなアニメーション
- 重要な変更を優先して表示
- キーボード操作にも対応できる拡張性

### 画面構成
1. Header：製品名・環境情報
2. Toolbar：表示モード切り替え
3. Canvas：インフラ構成グラフ
4. Details Panel：選択リソースの詳細
5. Findings Panel：検出した確認事項の一覧

## 6. 非機能要件

### NFR-001：セキュリティ
- 入力したTerraform JSONは外部サーバーへ送信しない
- ローカルホストでUIを提供する
- 診断処理を原則読み取り専用とする
- 元のJSONの全属性をUIへ送信しない
- 必要な属性だけを抽出する許可リスト方式を採用
- sensitive / unknown属性を適切に処理する
- 秘密情報をログやエラーに出力しない
- 外部のJavaScript CDNや利用状況送信機能を初期版では使用しない

### NFR-002：パフォーマンス
- 初期目標：100リソース規模のサンプルを快適に表示
- 大規模な構成では、ノードの折りたたみや表示対象の絞り込みを今後検討
- 初期表示速度はテスト環境を定めて計測する

### NFR-003：互換性
- Terraform 1.xのplan JSONを主な対象とする
- JSONの `format_version` を確認する
- 未対応のメジャーバージョンは明示的に拒否する
- 未知の項目や属性は安全に処理する
- Windows / macOS / Linuxでの利用を将来の目標とする

### NFR-004：保守性
- 解析エンジンと表示UIを分離する
- 診断ルールを追加しやすい構造とする
- サンプルデータによる自動テストを整備する

## 7. 技術構成

| 領域 | 採用候補 |
|---|---|
| CLI・解析 | Python |
| JSONバリデーション | Pydantic |
| グラフデータ処理 | NetworkX |
| UI | React / TypeScript |
| グラフ表示 | React Flow |
| 自動レイアウト | ELK または Dagre |
| テスト | pytest / Vitest |
| ソースコード管理 | GitHub |

### 処理フロー

```text
Terraform plan JSON
       |
       v
  JSON Parser
       |
       v
  Resource Model
       |
       v
  Graph Builder
       |
       +------> Security Rules
       |               |
       v               v
      Sanitized Graph Data
               |
               v
       React Flow UI
```

外部のクラウドサービスに依存せず、ローカルで解析・表示できることを優先する。

## 9. 受け入れ基準（完成判定）

v0.1は、以下を満たした時点で完成とする。

- [ ] 正常なTerraform plan JSONを読み込める
- [ ] 不正なJSONや未対応形式を適切に拒否できる
- [ ] 対応対象のリソースを識別できる
- [ ] 変更操作を正しく区別できる
- [ ] 構成グラフを描画できる
- [ ] ノードを選択して詳細情報を表示できる
- [ ] 3つの表示モードを切り替えられる
- [ ] 指定した診断ルールが正しいケースで警告を出す
- [ ] 問題のないサンプルには誤警告を出さない
- [ ] 秘密情報が画面・ログ・出力データへ漏れないことをテストできる
- [ ] 解析と表示がローカル環境で完結する
- [ ] 第三者がREADMEから起動できる

テストには秘密情報を含まない人工的なTerraformサンプルを使用する。

## 11. 初期の成果指標

技術面：
- 正常な入力を安定して解析できる
- 対応リソースについて変更内容を正しく表示できる
- 重大な情報漏えいや誤解を生む表示がない

ユーザー面：
- 外部のエンジニア5人程度に試用してもらう
- 実際の変更レビューで便利か確認する
- 利用者から改善要望を獲得する

事業面：
- 継続利用したいチームが存在するか調べる
- 有償導入の意思を確認する
- GitHub連携・チーム管理などの商用機能の需要を調べる
